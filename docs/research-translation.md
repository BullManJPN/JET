### AFM の節ごとの訳 (実マイクの節 139塊、非公開、平均7.5語)
- 文脈なし: 中央値255ms / p90 358ms / 最大439ms。約85%は下書きとして読める。順送り訳になる
- 文脈あり(直前の英語を渡す): **使えない**。約半数がプロンプトの例文をそのまま出力、直前の英語まで訳す例も多数 → AFMには短く単純なプロンプトだけ
- ガードレール誤検知 約2%("build the loops yourself," 等)、中国語混入あり("你知道")

### PCC (Private Cloud Compute) について
- 自作コマンド(swiftc の pccbench)からは呼べない: ModelManagerError 1046(エンタイトルメント不足)
- fm コマンドは Terminal.app で直接実行したときだけ PCC が動く。Python等のプログラムから呼ぶと "Please use the Terminal app" で拒否 → **この制限はすり抜けない方針**
- 正式に使う条件(developer.apple.com/private-cloud-compute): App Store Small Business Program 登録 + 初回DL 200万未満 + エンタイトルメント申請・割当。App Store配布アプリで使用、テストは TestFlight/アドホック。年会費(約1.3万円)が必要なので、申請は後で判断

### 調査メモ(翻訳まわり)
- AFM アダプター学習ツールは 26.0.0 が最終版で macOS 27 非対応 → 追加学習の道は現状なし
- ローカル翻訳特化モデル候補: PLaMo 2 Translate(約10B、英日特化、ライセンス要確認、速度未測定)
- Gemini Live Translate: 音声入力→翻訳音声。話している途中から訳すが、先読みの有無は非公開

## 最終訳テスト (10/28)  `research/sim/final_test.py`
Haikuで79単位(区間/先出し単位)を訳した。入力 = 訳す英語 + 直前2単位の英語 + 直前の最終訳(自分の出力、直列) [+ 用語集]
- **用語集あり: 効果小・副作用あり → 不採用**。Claude表記が直ったのは一部(Claod, claots)だけで、Quad/COVID と人名は直らず。崩れた文に詫び・質問を返す例が2件、英単語の混入が増加、入力トークン約1.7倍
- 3条件の比較(同じ79単位): 旧プロンプト / robust(聞き取りにくくても訳だけ出す)/ **robust_en(+固有名詞は英語のまま)**
  - 所要時間は3条件とも同じ: 中央値 約0.93-0.95s / p90 約1.25s / 最初の文字まで 約0.57s / 最大1.5s。**最終訳の遅延見込み(約1.9s)は維持**
  - 英語にClaudeを含む11単位で、訳が英語「Claude」/ カタカナ「クロード」: 旧 5/6、robust 7/4、**robust_en 10/1**
  - robust系は "COVID related" を「AIには関連が…」と最善の推測に直した(旧は「COVID関連」)
  - 詫び・質問の返答は用語集なしでは0件(「メタ応答?」の自動判定1件は誤検出)→ 「訳だけ出す」指示が崩れた文を防ぐ効果は未確認。保険として残す
  - robust_en は英語と日本語の間に半角スペースが入ることがある("Quad が"、"MLX のチーム") → 実装時に後処理で除去
- 直らなかった誤認識: Quad(別名表に quad を追加して解決、再テストは省略)、登壇者の人名(人名と判断)、聞き違い1件(未解決・意図不明)

## 下書きプロンプトの比較 (10/29)  `jetcli --draft-bench` / `research/sim/draft_score.py`
**結論: 例文(few-shot)なし + greedy を採用。** 翻訳モデルは AFM のまま変えない方針で、プロンプトで限界まで引き出す方向で調べた。
- テストセット(非公開): 10/29 の live の節(公開動画 4本)464件 + 実マイクの節 86件 = 550件(重複なし)。本番と同じ AFMDraft(プロンプト組み立て・例文の除去・安全策)で訳す
- 採点: Haiku 4.5 が A(趣旨が伝わる)/ B(一部ずれる)/ C(意味が違う・不明)、E は安全策で英語表示。最初の採点は「英語の聞き間違いで本来の意味を推測できていない」まで C にしていたので、**英語自体が崩れているかの印(asr)を別に付けさせ、英語がまともな約410件で比べる**ように直した
- ぶれ: 同じ設定2回で約1ポイント。採点も文ごとにぶれる(「スタックは4層です」B と「4つの層があります」C など)。数ポイント以上の差だけを信じる

| 案 | 読める(英語がまとも) | C | 例文の漏れ | 時間 中央値 / p90 |
|---|---|---|---|---|
| 今まで(例文3件・確率的) | 81.6〜82.5%(全体) | 12〜13%(全体) | 5〜7 | 274〜279 / 370〜375 ms |
| greedy(例文3件) | 90.3〜90.5% | 3.7〜3.9% | 6 | 269 / 363 ms |
| v2 例文の順番を変える | 89.7% | 4.7% | **37** | 279 / 375 ms |
| v3 失敗の型の例文を足して8件 | 56.5% | **39.3%** | **212** | 394 / **887** ms |
| sys2 指示に「否定・比較・数を変えない」を足す | 90.7% | 4.7% | 1 | 288 / 371 ms |
| scene1 / scene2 場面の設定(IT企業の会議、技術の話題) | 91.0% / 90.0% | 3.7% / 4.2% | 8 | 287〜288 / 368〜383 ms |
| **v0 例文なし(採用)** | **93.2%** | **2.7%** | **0** | **257 / 350 ms** |
| v1a 断片の例文1件 | 90.0% | 5.3% | 0 | 272 / 351 ms |
| v1b 固有名詞の例文1件(MCP/Slack) | 93.4% | 1.9% | 0 | 272 / 352 ms |

- **AFM は例文を「写す材料」として扱う**: 例文を増やすほど混入が増え、取り除いた残りも崩れる。漏れるのは常に最後の例文(v2 で最後を「Thanks for coming in today.」にすると漏れが6→37件)
- 例文なしでも固有名詞(Claude, Anthropic, MCP, API, MLX, Xcode, Ollama, GitHub, Python, Slack)は 100% 英語のまま(76/76)。指示文だけで足りる
- v0 と v1b は互角(判定が分かれた104件で v1b 54 / v0 50)。単純で漏れが構造的に起きない v0 を採用
- 場面の設定は訳を入れ替えるだけ(scene1 は改善33 / 悪化34)。「bag → バグ」「batting → バッチ処理」は直らない。AFM は英語の字面に強く引っ張られる
- greedy は質が同等で少し速く、同じ入力に同じ訳を返す(比較にも向く)
- 例文の除去(stripFewshotEcho)は保険として残す。中国語の混入「地址」はかなと一緒に出たので今の判定では見逃す(低頻度)
- AFM の誤訳の型(例文なしでも残るもの): 数量(100s of 1000s → 100から1000)、比較・否定(one at a time / too large to fit で意味が逆)、文脈がないと決まらない語(Metal → 金属)。完全な誤訳の大半は入力の英語の崩れが原因(`research-asr.md`「途中経過の崩れた語」)
- 追加学習: Apple が「OS 27 からアダプターはサポートしない」と回答(Developer Forums、2026年6月)。追加学習の道は閉じた
- 参考(採用しなかった方向): 翻訳専用の小型モデル LFM2-350M-ENJP-MT(0.4B、英日専用)、TranslateGemma 4B(2026年1月)。AFM のまま進める方針なので未測定
- 手での判定(10/29 公開動画238件、流れ型): A 67% / B 19% / C 9% / 英語表示 5%。C の22件のうち約16件は英語の聞き間違いが原因、AFM 自身の誤訳は約6件

## 節の区切り方の比較 (10/29 15:40)  `research/sim/clause_rules.py` → `research/sim/clause_score.py`
録音5本。AFM 下書き(例文なし・greedy)を区間ごと(335区間)につないで Haiku で採点。
| 案 | 内容 | 節 | A(英語がまとも) | 読める | C | 語ごとの待ち 中央値 / p90 |
|---|---|---|---|---|---|---|
| v0 | 今(and/or/which 等で閉じる、14語で切る) | 654 | 42.5% | 87.1% | 12.9% | 2.36 / 4.62秒 |
| v2 | and/or は次の語が主語らしいときだけ、which/where では閉じない | 610 | 46.8% | 89.3% | 10.7% | — |
| v3 | v2 + 14語上限で前置詞・冠詞などの後では切らない | 611 | 47.9% | 88.9% | 11.1% | 2.43 / 4.74秒 |
| **v4** | v3 + 上限18語 | 551 | **55.7%** | **90.0%** | **10.0%** | 2.48 / 4.97秒 |
- 全件では 読める 81.8% → 86.0%、C 18.2% → 14.0%(v0 → v4)。AFM の時間 p90 363 → 401ms
- 上限を22・30語にしても節はほとんど変わらない(18語以上の節 22 → 34)。語ごとの待ちは話してから節が閉じるまで(音声認識の遅れ込み)

### 続き: 間のあと2行続けて出る問題 (10/29 16:20)
- 実機で長い待ちのあと1秒以内に次の行が出たのが21か所。原因は18語上限で切った残り(1〜2語の短い行)と、and の後の the/their で名詞のつながりを切ったこと
- 6録音484区間(英語がまとも426): v4 A 56.8% / C 9.6% → v5(and の後は代名詞だけ)58.7% / 9.6% → **v6(v5 + 18語を超えても3語まで句読点を待つ)62.2% / 9.4%**。続けて出る 99 → 72、3語以下の文末 66 → 49(シミュレーション)。AFM の時間 p90 396 → 412ms
